# AgentHub 比赛计划

## 1. 赛题结论

`AgentHub - 多 Agent 协作平台` 的核心不是做一个普通聊天机器人，而是做一个以 IM 聊天为主入口、强调人和 AI 协作范式、能够围绕产物持续迭代的多 Agent 协作系统。

当前项目需要对齐的最新要求包括：

- 交互主入口必须是聊天工作台，而不是 Workflow Canvas
- 系统需要体现 `Orchestrator` 作为主 Agent 的调度能力
- 至少接入 2 个主流 Agent 平台
- 要围绕代码、网页、文档、PPT 等产物做预览、编辑和二次交互
- `Spec / Skill / Rules` 等 AI 协作资产是高权重考察点
- 最终提交不仅看代码，还看产品设计、技术设计、协作记录和 Demo 呈现

## 3. 课题背景与目标

### 3.1 课题名称

`AgentHub - 多 Agent 协作平台`

### 3.2 课题背景

课题要求构建一个简化实战版的多 Agent 协作平台。平台采用 IM 聊天作为核心交互范式，用户像使用飞书或微信一样，通过新建对话、发送消息、@ 指定 Agent、查看聊天流中产物的方式完成复杂任务。

### 3.3 课题目标

目标不是单纯做一个问答型产品，而是构建：

- 人与 AI 的协作平台
- 多 Agent 的协作调度系统
- 围绕 Artifact 持续迭代的产品工作台

更准确地说，项目要证明：

- 人如何指挥多个 Agent 协作开发
- 主 Agent 如何拆解任务、分派任务、聚合结果
- 产物如何作为后续迭代的核心上下文被继续修改

## 4. 最新课题要求

### 4.1 交互体验要求

系统需要具备基础 IM 工作台能力：

- 对话列表
- 单聊模式
- 群聊模式
- 消息流
- 输入区

消息与交互能力需要覆盖：

- 文本
- 代码块
- 文件附件
- 网页预览卡片
- Diff 视图卡片
- 部署状态卡片

还需要支持：

- 产物预览
- 产物编辑
- 二次交互
- 消息回复、引用、重新生成
- 上下文管理
- 部署到第三方平台的展示或链路设计

### 4.2 主 Agent 要求

主 Agent 即 `Orchestrator`，角色类似 `PM / PMO`，需要负责：

- 理解用户问题
- 拆解复杂任务
- 分派给子 Agent
- 汇总执行结果
- 并行调度
- 失败降级
- 代码冲突处理

### 4.3 多 Agent 接入要求

系统至少需要接入两个主流 Agent 平台，示例包括：

- Cloud Code
- Codex
- Open Code

还需要支持：

- 用户自建 Agent
- 每个 Agent 有头像、名称、能力标签
- 每个 Agent 在聊天列表里像独立联系人一样可被识别和调用

### 4.4 产物预览与编辑要求

系统要支持在聊天流中内联展示产物，并继续围绕产物修改。覆盖的产物类型包括：

- 网页预览
- 文档渲染
- PPT 浏览
- 代码编辑
- Diff 视图
- 版本历史

同时支持：

- 引用某段文档或代码继续交给 Agent 处理
- 二次交互和二次修改
- 围绕已有 Artifact 持续迭代

### 4.5 多端支持要求

多端支持是加分项，不是 P0 强制项，但设计上要考虑：

- Web 端：主力端，完整 IM 体验和全功能
- 桌面端：本地文件访问、通知、Agent 进程管理
- 移动端：轻量 IM 体验、审批确认、产物预览

多人协作场景下，还需要考虑：

- 多端消息同步
- 冲突解决

## 5. 考察要点

| 维度 | 权重 | 评判重点 |
|---|---:|---|
| AI 协作能力 | 30% | 是否沉淀出 `Spec / Skill / Rules` 等协作规范与协作范式 |
| 功能完整度 | 25% | IM 核心体验是否流畅，多 Agent 调度是否跑通，badcase 是否有处理 |
| 生成效果质量 | 20% | 聊天 UI、产物预览、整体展示效果 |
| 代码理解度 | 15% | 答辩时能否解释架构选型和核心逻辑 |
| 创意创新与产品感 | 10% | 是否有超预期功能点、产品设计是否完整 |

结论很直接：

- 评分最高的是 `AI 协作能力`
- 不是只看模型接得多不多
- 而是看协作方法是否沉淀成产品和文档资产

## 6. 交付物要求

最终交付物包括：

- 产品设计文档
- 技术文档
- 可运行 Demo
- AI 协作开发记录
- 3 分钟 Demo 视频

其中 AI 协作开发记录可以包含：

- Specs
- Skill
- Rules
- Harness
- 面向 Agent 的协作规范

当前要求明确：

- 不强制提交完整对话记录
- 更希望仓库本身是 `agent-friendly`
- 可以沉淀个人或团队与 AI 协作的方法

## 7. 对 AgentHub 的实际约束

结合当前要求，`AgentHub` 应按以下边界推进。

### 7.1 P0 必做

- IM 工作台
  - 对话列表
  - 单聊
  - 群聊
  - 消息流
  - 输入区
- 主 Agent `Orchestrator`
  - 任务理解
  - 任务拆解
  - Agent 路由
  - 结果聚合
- 多 Agent Adapter
  - 至少支持 2 个主流 Agent 平台的统一接入设计
- 上下文管理
  - 聊天历史
  - Pinned Context
  - Artifact Handoff
  - Handoff Summary
- Artifact 预览
  - Code Card
  - Web Preview Card
  - File Card
  - Markdown Card
- 用户自定义 Agent
  - 名称
  - System Prompt
  - Tool Tags
  - Capability Tags
- AI 协作资产
  - Task Spec
  - Skill
  - Rules
  - Collaboration Protocol

### 7.2 P1 应做

- Agent 状态展示
- Reviewer Flow
- Handoff Summary 可视化
- 产物二次修改链路
- 简单部署状态卡片

### 7.3 P2 加分项

- Diff View
- Version History
- Deploy Action
- Web / Desktop / Mobile 的多端方案
- PPT 浏览
- 更细的多人协作与冲突解决说明

## 8. 允许与限制

当前明确：

- 开发语言不限
- 可以基于已有项目开发

但最终仍然考察：

- 代码是否真正能解释
- 功能设计和产品设计是否对应
- 是否有自己的思考
- 是否形成完整闭环

也就是说，可以借鉴已有项目，但不能只做拼接，最后必须是一个能自圆其说、可运行、可答辩的完整作品。

## 9. 当前项目策略

对 `AgentHub` 来说，当前最合理的推进策略仍然是：

- 以 Web 端作为主交付端
- 以聊天工作台作为唯一主入口
- 先把多 Agent 协作链路跑通
- 再补围绕 Artifact 的持续迭代
- 把 `Spec / Skill / Rules` 产品化展示出来

一句话总结：

> 先证明“多 Agent 能协作完成任务并围绕产物持续修改”，再考虑做得多炫。

## 10. 立即执行项

基于当前要求，现阶段最应该优先确保：

1. 文档与赛题要求完全对齐
2. Demo 主链路覆盖：
   - 用户发起任务
   - Task Spec 生成
   - Orchestrator 拆解
   - Agent 分工
   - Artifact 产出
   - Reviewer 检查
   - Artifact 二次修改
3. 产品设计、技术设计、AI 协作记录三者保持一致
4. 所有答辩重点都能在界面中被“看见”，而不是只写在文档里
