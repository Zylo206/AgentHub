# AgentHub 比赛计划

## 1. 项目定位

AgentHub 是一个面向 AI 全栈挑战赛的、以 Web 为主的 IM 式多 Agent 协作平台。

项目目标不是做一个普通聊天机器人，而是做一个“人和多个 Agent 围绕任务与产物协作”的系统：用户通过聊天发起需求，Orchestrator 负责任务拆解、分派与汇总，代码、网页、文档等产物在同一条协作链路里可见、可预览、可继续修改。

## 3. 产品策略

### 核心产品描述

AgentHub 让用户像使用飞书或微信一样，与多个 AI Agent 在聊天中协作完成任务，并且让生成的代码、网页、文档等产物始终留在聊天流中，支持预览和持续迭代。

### 产品原则

- Web 优先，MVP 阶段不分散精力到桌面端和移动端
- 聊天优先，不把工作流画布作为主入口
- 产物优先，不做只返回文字的问答系统
- 协作结构化，不做临时拼接式模型切换
- 执行过程可解释，关键步骤必须能在 Demo 中看见

## 4. 项目范围

### P0 必做

| 模块 | 范围 |
|---|---|
| IM 工作台 | 会话列表、单聊、群聊、输入框、消息流 |
| Orchestrator | 任务理解、任务拆解、任务分派、结果汇总 |
| 多 Agent 适配层 | 至少接入 2 个主流 Agent 平台 |
| 上下文管理 | 聊天历史、Pin 长期上下文、产物交接 |
| 产物预览 | 代码卡片、网页预览卡片、文件卡片 |
| 用户自建 Agent | 名称、System Prompt、工具标签、能力标签 |
| AI 协作资产 | Spec、Skill、Rules、协作协议 |

### P1 应做

| 模块 | 范围 |
|---|---|
| Agent 状态展示 | 等待中、执行中、已完成、失败 |
| 交接摘要 | 可见的 Agent 间上下文转交 |
| Reviewer 流程 | 基于验收标准进行检查 |
| 知识库桥接 | 轻量文档挂载或检索能力 |

### P2 加分项

| 模块 | 范围 |
|---|---|
| Diff 视图 | 对比产物前后版本差异 |
| 部署操作 | 返回部署状态或预览 URL |
| 版本历史 | 展示产物演进过程 |
| 多端方案 | 先只体现在设计文档，不强制落地 |

## 5. 架构方向

### 主仓库

`E:\CodeProject2\AgentHub`

### 实现原则

- 采用 Web 优先的工作台架构
- 采用聊天优先的产品入口，不以 Workflow Canvas 作为主入口
- 采用 Specialist Agent + Reviewer 的协作模型
- 采用统一 Adapter 层屏蔽不同 Agent 平台差异
- 采用轻量知识能力，不在 MVP 阶段引入复杂基础设施

### 规划模块

| 层级 | 模块 |
|---|---|
| 前端 | 聊天工作台、Agent 创建页、预览面板、任务 Spec 卡片 |
| 后端 | API 层、Orchestrator 服务、上下文管理、产物服务、适配器层 |
| 协作资产 | Spec、Skill、Rules、协作协议、Demo 记录 |

## 6. AI 协作能力计划

这是比赛中权重最高的维度，必须产品化，不能只停留在文档说明。

### 需要在系统里可见

| 资产 | 体现方式 |
|---|---|
| Spec | 用户需求进入后自动生成任务 Spec 卡片 |
| Skill | Agent 分配时展示使用的能力画像 |
| Rules | 在路由和交接逻辑中明确体现命中的规则 |
| 协作协议 | 用 Orchestrator -> Specialist -> Reviewer 的流程体现 |

### 需要在仓库里交付

| 目录 | 用途 |
|---|---|
| `docs/spec/` | 任务 Spec 模板与实际任务 Spec |
| `docs/skills/` | Agent Skill 定义 |
| `docs/rules/` | 路由规则与交接规则 |
| `docs/collaboration/` | 协作协议与流程规范 |

### 需要在 Demo 中展示

1. 用户提交一个复杂任务
2. 系统自动生成任务 Spec
3. Orchestrator 拆分任务
4. 根据 Skill 和 Rules 分配给不同 Agent
5. 各 Agent 在聊天流中返回产物
6. Reviewer 按验收标准检查
7. 用户继续围绕产物发起修改

## 11. Demo 主线脚本

Demo 必须围绕一条稳定场景展开：

1. 用户提出一个多步骤任务
2. AgentHub 自动生成任务 Spec
3. Orchestrator 拆解并分配任务
4. 多个 Agent 返回不同产物
5. 代码和文档卡片在聊天中内联展示
6. Reviewer 按验收标准检查
7. 用户追加一次修改需求
8. 系统返回最终结果

## 12. 风险与缓解

| 风险 | 影响 | 缓解方式 |
|---|---|---|
| 范围过大 | Demo 不稳定 | 尽早冻结 P0，主动砍掉非必要 P2 |
| 平台集成工作过重 | 核心链路延期 | 先做薄适配层，优先打通流程 |
| 协作资产只停留在文档 | AI 协作分数不高 | 必须把 Spec/Skill/Rules 放进聊天 UI 中展示 |
| 后端复杂度投入过多 | 产品感不足 | 优先做看得见的用户流程，不先追后台完美 |
| 最终 Demo 不稳定 | 提交风险高 | 2026-06-07 前锁定演示路径并完成彩排 |
